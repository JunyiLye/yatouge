# Code Review Findings — 線上 1 對 1 對戰

結論：沒有 Critical。資料驗證很完整，沒有 HTML 注入或 prototype pollution 的途徑，單人模式不受影響，正常流程中 room API 的用法也正確。但在真實平台上的錯誤與邊界情況處理不足，有 8 項 Important，其中前 4 項審查者建議上傳前修好。另有 11 項 Minor。處置等使用者決定。

審查者：fresh-context code-reviewer subagent（唯讀，沒有開瀏覽器）。`node --test` 126/126。

## Important
- **CR1 — 對戰房斷掉時沒有處理**（`netFail` 約 1916–1923 行、`startMatch` 2005 行）
  - 平台重連後若無法重新加入房間，會送出 `upstream_error` 等錯誤碼，但程式沒處理，對戰會卡住。
  - 建議：收到錯誤就回大廳並提示連線中斷；`join` 被拒絕（`not_permitted`）時隱藏線上按鈕。
- **CR2 — 永久性錯誤卻顯示「正在重新連線」**（1914–1922 行）
  - `revoked`、`not_granted` 這類錯誤在這次載入中不會恢復。
  - 建議：遇到這類錯誤就離開對戰，回到單人模式。
- **CR3 — 對手短暫從名單消失就被判定離開**（`pvpPoll` 2087–2096 行）
  - 平台會定期重新整理連線，短暫消失是正常的，但目前這樣就會中斷倒數，或讓結果變成「對手已離開」。
  - 建議：對手連續消失約 2 秒才判定離開。
- **CR4 — 第三人可以在比賽中途頂替對手**（`pvpPoll` 2089–2094 行）
  - 對手中途離開後，開房者會把任何加入房間的人當成新對手，而房間名稱是公開的。
  - 建議：只在 waiting 或 ready 狀態才接受新對手。
- **CR5 — 開房者沒有檢查對方的賽道**（`pvpCheck` 1986 行）
  - 惡意的開房者可以每秒切換賽道約 30 次，讓對方一直重建場景，造成卡頓。
  - 建議：要求雙方賽道一致，並限制賽道切換的頻率。
- **CR6 — 名稱查詢可能被重複呼叫**（`resolveNames`）
  - 建議：只在名單改變時查詢，並標記查詢中的 id。
- **CR7 — 進入房間面板時沒有管理焦點**
  - 鍵盤和螢幕閱讀器的使用者會失去位置。
  - 建議：進入房間時把焦點移到「準備」按鈕。
- **CR8 — 對戰的接線邏輯沒有測試**
  - 包括 `ingest`、`pvpPoll`、`oppGone`、`pvpBump`。
  - 建議：抽成純函式並補測試。

## Minor
- CR9：發布版也可以用 `?mockroom=1`。只會連到同一個瀏覽器的分頁，不是安全漏洞，但沒登入的人也會看到線上按鈕。建議只在 localhost 啟用。
- CR10：`use('room')` 和 `use('user')` 是依序等待，最慢可能 20 秒才顯示按鈕。建議並行。
- CR11：樣本以收到的時間為準，不是傳送端的時間，背景分頁的資料可能擠在一起。休閒對戰可以接受。
- CR12：背景分頁的開房者不會開始倒數（瀏覽器行為）。驗收時要注意。
- CR13：結果畫面在 60 秒後顯示「對手未完賽」，如果對手之後才衝線，結果可能從勝利變成落敗。
- CR14：已翻譯的提示文字在切換語言後不會更新。實際上不太會發生。
- CR15：`validPeerId` 假設 peer 標籤的格式。如果真實平台的格式不同，可能永遠無法同步。建議只檢查長度和控制字元。
- CR16：大廳一打開就顯示「沒有房間」，應該等約 1.5 秒。
- CR17：對手換車型或顏色時，舊的模型沒有釋放，會慢慢累積記憶體。
- CR18：理論上可以用相同的房間名稱擠掉別人的房間。風險低。
- CR19：計畫中寫的「傳送端時間戳記」沒有實作，`pvpFree` 字串沒有使用。
